# План работ над FPGA-картриджем с Flash-памятью для Game Boy

**Обновлено:** 2026-09-07

**Назначение:** последовательная первичная проверка с измеримыми критериями
готовности

## Контекст

Текущее состояние и подтверждённые результаты — в [STATUS.md](STATUS.md),
владение памятью и режимы — в [ARCHITECTURE.md](ARCHITECTURE.md).
Первый прототип собирается проводным монтажом. Финальная PCB, MBC и сохранения
не входят в текущий этап.

Для этапов чтения/стирания/записи добавлена [реализация программатора](PROGRAMMER.md).
Есть RTL-симуляция, host-тесты и UF2. Этапы ниже остаются критериями аппаратной
приёмки; новый JEDEC и работа сквозного тракта на стенде пока не подтверждены.

## Цель ближайшего цикла

Записать небольшой известный файл `.gb` по пути:

```text
Компьютер → USB → RP2040 → SPI → FPGA → MX29LV320E
```

Затем прочитать весь записанный диапазон обратно, получить успешный результат
проверки, перейти в режим `GAME` и воспроизвести результат внутреннего ПЗУ:

```text
логотип Nintendo → чёрный экран
```

## Последовательность работ

Стартовый сброс исправлен, тест Flash завершился PASS, в том числе после
полного выключения и включения питания. Проверенный выпуск
[flash-bringup-pass](../releases/fpga/flash-bringup-pass/MANIFEST.md) сохранён. Далее
подготовить владение шиной (этап 5), запустить SPI (этап 6) и чтение до ПК
(этап 7). Этапы 1–3 ниже остаются перечнем проверок для воспроизведения и
смены монтажа; общий результат теста не закрывает автоматически каждый их
критерий. Этап 4 относится к интеграции контроллера в программатор.

### Этап 0. Сохранить рабочую базовую конфигурацию — выполнено

Исходник сохранён в `fpga/targets/internal_rom/`, а проверенный артефакт сборки
и ключевые отчёты — в `releases/fpga/internal-rom-baseline/`. Содержимое
тестового ПЗУ нельзя менять до первого успешного запуска из внешней Flash.

**Критерий успеха:** конфигурацию можно повторно прошить в FPGA и получить на
Game Boy тот же результат.

### Этап 1. Проверить подключение MX29LV320E

Проверить адресные линии, `D0-D7`, `CE#`, `OE#`, `WE#`, питание, развязывающие
конденсаторы и служебные входы. Подтвердить режим x8 по техническому описанию
точного варианта Flash. До подачи питания проверить отсутствие коротких
замыканий и правильность соединений.

Новые назначения выводов нельзя выбирать по памяти. Сначала нужно проверить
корпус и доступные PIO, затем согласованно обновить схему и LPF.

**Критерий успеха:** соединения проверены, управляющие линии имеют безопасные
состояния, а `WE#` не может самопроизвольно активироваться при включении или
конфигурации FPGA.

### Этап 2. Реализовать только чтение Flash

В репозитории есть самостоятельный тест
`fpga/targets/flash_bringup/top.v`, способный изменять память. Для первого
включения он не подходит: нужна отдельная конфигурация только для чтения, в
которой отсутствуют доступные последовательности стирания и записи.

Минимальный консервативный цикл чтения:

```text
установить адрес
→ активировать CE#
→ активировать OE#
→ выдержать требуемое время
→ принять D0-D7
→ деактивировать OE# и CE#
```

Сначала следует использовать заведомо большие интервалы ожидания.

**Критерий успеха:** FPGA стабильно получает одинаковые данные с выбранных
адресов, а конфликт управления шиной данных отсутствует.

### Этап 3. Проверить тракт FPGA ↔ Flash

Организовать простой вывод результатов контроллера чтения. Если техническое
описание установленной микросхемы это допускает, прочитать идентификаторы
производителя и устройства, после чего явно вернуться в обычный режим чтения.
Проверить несколько адресов и границы выбранных диапазонов.

**Критерий успеха:** подтверждены адресная шина, направление `Flash → FPGA` на
`D0-D7`, управление `CE#/OE#` и повторяемость чтения.

### Этап 4. Подготовить контроллер стирания и записи Flash

Использовать проверенный `flash_bringup` со стартовым сбросом как основу.
Низкоуровневые циклы уже выделены в `rtl/mx29_bus.v`; для программатора
нужен интерфейс отдельных операций вместо автономной тестовой последовательности.
Проверить адреса секторов и смоделировать безопасные состояния.

Минимальные операции:

- чтение;
- стирание выбранной области;
- запись байта;
- опрос готовности;
- тайм-аут и явный код ошибки;
- возврат в обычный режим чтения после успеха или ошибки.

Последовательности команд и временные параметры берутся из технического
описания точного варианта MX29LV320E.

**Критерий успеха:** симуляция или стендовый тест показывает правильные циклы
адреса, данных и управления; `WE#` активируется только в `PROGRAMMER`.

### Этап 5. Зафиксировать безопасное владение шиной

Реализовать взаимоисключающие режимы по [архитектуре](ARCHITECTURE.md#режимы-работы).

Для первого прототипа допустимы перемычка, отдельный вход или отдельная сборка
FPGA. Вариант выбирается с учётом питания и доступных выводов.

**Критерий успеха:** одновременное управление Flash двумя сторонами невозможно,
а выбранный режим однозначно наблюдаем.

### Этап 6. Запустить SPI между RP2040 и FPGA

FPGA target и прошивка RP2040 реализованы; подробный статус — в
[STATUS.md](STATUS.md). Выполнить подключение и
[аппаратную приёмку](SPI_BRINGUP.md#аппаратная-приёмка) на фиксированном
ответе версии без обращения к Flash. Команды памяти относятся к следующим этапам.

**Критерий успеха:** RP2040 многократно получает правильную сигнатуру без
ошибок передачи.

### Этап 7. Прочитать Flash по полному тракту

Добавить USB-команду чтения диапазона:

```text
Компьютер → USB → RP2040 → SPI → FPGA → Flash
Flash → FPGA → SPI → RP2040 → USB → компьютер
```

Несколько раз прочитать одни и те же диапазоны, пока ничего не стирая.

**Критерий успеха:** повторные результаты совпадают побайтово; компьютер
получает правильную длину и состояние операции.

### Этап 8. Выполнить первое стирание по полному тракту USB/SPI

Перейти в `PROGRAMMER`, стереть выбранный тестовый сектор и дождаться
завершения с тайм-аутом. Прочитать начало, середину и конец затронутой области.

**Критерий успеха:** проверенные байты находятся в стёртом состоянии, операция
завершается явным успехом, а Flash возвращается в обычный режим чтения.

### Этап 9. Записать тестовые последовательности

Сначала записать короткие комбинации с одиночными установленными и сброшенными
битами, затем 256-байтовую последовательность. Прочитать данные обратно по
полному тракту и сравнить.

При несовпадении вывести:

```text
адрес
ожидаемый байт
фактический байт
```

**Критерий успеха:** обе последовательности проходят полную побайтовую
проверку; повторный цикл стирания, записи и проверки также успешен.

### Этап 10. Записать известное тестовое ПЗУ

Использовать ровно тот образ, который уже работает из внутренней памяти FPGA.
Не добавлять MBC и не менять программу в том же эксперименте.

**Критерий успеха:** программатор сообщает правильный объём, завершает запись
без тайм-аута или ошибки и запускает проверку.

### Этап 11. Выполнить полную проверку

Прочитать весь записанный диапазон через реальный путь
`Flash → FPGA → RP2040 → компьютер` и побайтово сравнить с исходным `.gb`.
Внутренний буфер отправителя использовать для проверки нельзя.

Ожидаемый отчёт:

```text
записано:  N байт
проверено: N байт
результат: УСПЕХ
```

При первой ошибке вывести адрес, ожидаемое и фактическое значения. Запуск на
Game Boy при ошибке запрещён.

**Критерий успеха:** весь образ совпадает без единой ошибки.

### Этап 12. Запустить Game Boy из внешней Flash

Отключить программатор, безопасно перейти в `GAME`, полностью перезапустить
питание и выдавать байты ПЗУ из MX29LV320E.

**Критерий успеха:** воспроизводится базовый результат:

```text
логотип Nintendo → чёрный экран
```

Это закрывает этап загрузки Game Boy из внешней Flash.

### Этап 13. Подтвердить выполнение кода

После успешного запуска подготовить диагностическое ПЗУ с однозначным
визуальным результатом: заливкой, полосами, шахматным узором или сменой
палитры. Сначала проверить его во внутренней памяти FPGA, затем записать во
Flash с полной проверкой и повторить опыт.

**Критерий успеха:** внутреннее и внешнее ПЗУ дают одинаковый диагностический
результат.

## Что пока не делать

До завершения работы с внешней Flash не следует:

- реализовывать MBC и переключение банков;
- подключать F-RAM и сохранения;
- добавлять передачу сохранений по USB;
- разрабатывать автоматический арбитраж одновременного доступа;
- оптимизировать скорость SPI и Flash до стабильной работы на низкой скорости;
- заканчивать финальную PCB и компоновку корпуса;
- записывать полный образ 4 МБ, пока тестовый образ 32 КБ не проходит проверку;
- одновременно менять ПЗУ, интерфейс шины и контроллер Flash;
- фиксировать неподтверждённые назначения выводов.
