# План испытаний

## Уровни подтверждения

- **Проверено:** результат повторён на реальном устройстве или сохранён
  автоматизированным тестом.
- **Реализовано:** исходник или схема существует, но обязательный тест не
  пройден.
- **Запланировано:** зафиксирован только замысел.

Статус нельзя повышать до «проверено» без фиксации конфигурации, ревизии
артефакта, испытательного стенда и наблюдаемого результата.

## Сверка LPF

Сверка выполняется для каждой конфигурации отдельно с учётом
[приоритета источников](README.md#приоритет-источников):

1. После синтеза открыть в Diamond `Spreadsheet View -> Port Assignments`.
   Diamond формирует полный список портов верхнего уровня автоматически;
   поддерживать отдельный список вручную не нужно.
2. Убедиться, что для каждого аппаратного порта в этой таблице заданы правильный
   вывод FPGA и электрический стандарт. В LPF им соответствуют записи
   `LOCATE COMP ... SITE ...` и `IOBUF`.
3. В схеме `hardware/cartridge/cartridge.kicad_sch` найти FPGA `U5` и для
   каждого порта сопоставить имя цепи и номер вывода с `SITE` в LPF. Шины нужно
   проверять поразрядно: например, `gb_a[0]` нельзя считать проверенным по
   совпадению только имени шины `gb_a`.
4. Проверить, что выбранные в Diamond устройство и корпус совпадают со схемой:
   `LCMXO2-1200HC-4TG100C`.
5. Убедиться, что в LPF нет ограничений для отсутствующих портов, а среди
   аппаратных портов `top` нет портов без назначения вывода. Предупреждения
   Diamond о выводах и стандартах ввода-вывода должны быть разобраны до
   программирования устройства.
6. После сборки сохранить отчёт о назначении выводов и сравнить его с LPF;
   результат сверки зафиксировать вместе с именем конфигурации и исходным
   коммитом.

Изменять схему только для устранения расхождения с LPF нельзя. Если найдено
расхождение, сначала нужно установить ожидаемое соединение по правилам
приоритета источников, а затем исправить зависимый артефакт.

## Проверка FPGA

Для каждой конфигурации сборки:

1. выполнить синтез;
2. выполнить описанную выше сверку LPF;
3. выполнить отображение логики, размещение, трассировку и генерацию потока
   конфигурации;
4. сохранить количество ошибок и предупреждений и отчёт временного анализа;
5. для асинхронных шин проверить заданные максимальные комбинационные задержки,
   а не только общий результат временного анализа.

Симуляция контроллера Flash должна покрывать чтение, последовательности команд,
тайм-аут, возврат в обычный режим чтения и невозможность одновременного
управления шиной несколькими устройствами.

## Проверка аппаратной части

До подачи питания:

- выполнить ERC схемы и DRC PCB;
- проверить сопротивление между питанием и землёй и целостность собранных цепей;
- проверить неактивные состояния Flash `CE#/OE#/WE#`, F-RAM `CE#/OE#/WE#` и
  `OE/DIR` преобразователей уровней;
- убедиться, что USB и Game Boy не могут питать друг друга обратным током.

## Последовательность первичной проверки

1. Стабильно читать Flash без команд стирания и записи.
2. Прочитать идентификатор, если это допускает техническое описание
   установленной микросхемы.
3. Проверить SPI на фиксированном ответе версии без обращения к памяти.
4. Несколько раз прочитать один диапазон Flash по полному пути до компьютера.
5. Стереть только выбранный тестовый сектор и проверить его состояние.
6. Записать короткие последовательности проверки линий данных и адреса, затем
   прочитать их обратно.
7. Записать известное небольшое тестовое ПЗУ и проверить каждый байт.
8. Перейти в `GAME` и воспроизвести результат внутреннего ПЗУ.

При несовпадении нужно вывести как минимум адрес, ожидаемый и фактический байт.
Запуск образа, не прошедшего полное чтение и сравнение, запрещён.

## Данные выпуска

Каталог выпуска должен содержать артефакт, исходный коммит, версию набора
инструментов, имя конфигурации, SHA-256 и соответствующую сводку DRC или
временного анализа.
