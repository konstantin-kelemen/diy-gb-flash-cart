# Game Boy FPGA Flash Cartridge — NEXT STEPS

**Prepared:** 2026-09-02  
**Purpose:** контекст и рабочий план для продолжения проекта в новом чате

---

## 1. Краткий контекст

Цель проекта — flash-картридж для оригинального Game Boy. FPGA MachXO2 реализует интерфейс cartridge bus, в дальнейшем MBC и управление памятью. ROM хранится во внешней параллельной NOR Flash `MX29LV320E` объёмом 4 MB. RP2040-Zero обеспечивает USB-связь с компьютером и передаёт FPGA данные для записи. FRAM `FM28V100-TG` позже будет хранить saves.

Первый прототип собирается на проводах. Финальная PCB, MBC и saves пока не являются текущей задачей.

---

## 2. Что уже доказано на реальном железе

- FPGA `LCMXO2-1200HC-4TG100C` программируется и запускает тестовый design.
- Собран прототип `Game Boy connector → SN74LVC8T245 → FPGA`.
- FPGA эмулирует минимальный ROM непосредственно из внутренней памяти.
- На реальном Game Boy появляется Nintendo logo, затем black screen.
- Этот результат является подтверждённым milestone: Game Boy читает ROM через connector, level shifters и FPGA достаточно корректно для прохождения проверки логотипа.

Ограничение результата: black screen не считается отдельным доказательством полноценного выполнения пользовательского кода. Для текущего перехода к внешней Flash достаточно воспроизвести тот же известный результат, не меняя одновременно сам ROM.

## 3. Текущая архитектура

```text
GAME MODE

Game Boy
   ↓ 5 V cartridge bus
SN74LVC8T245 x4
   ↓ 3.3 V bus
MachXO2 FPGA
   ↓ parallel A/D/CE#/OE#
MX29LV320E


PROGRAMMER MODE

PC
   ↓ USB
RP2040-Zero
   ↓ SPI: SCK/MOSI/MISO/CS#
MachXO2 FPGA
   ↓ parallel A/D/CE#/OE#/WE#
MX29LV320E
```

Принятые решения:

- RP2040 ↔ FPGA работает по SPI.
- RP2040 не управляет параллельной Flash напрямую.
- FPGA формирует все циклы чтения, стирания и записи MX29LV320E.
- FPGA имеет два взаимоисключающих режима: `GAME` и `PROGRAMMER`.
- Для первого прототипа режим можно выбирать вручную или другим простым способом.
- В `GAME MODE` сигнал Flash `WE#` всегда неактивен.
- После любой записи ROM обязателен полный verify чтением через тот же тракт.
- Точные физические пины SPI и новых управляющих сигналов пока не назначаются без проверки pinout.

---

## 4. Главная цель ближайшего цикла

Записать известный небольшой `.gb` по пути:

```text
PC → USB → RP2040 → SPI → FPGA → MX29LV320E
```

прочитать весь записанный диапазон обратно, получить `VERIFY OK`, переключить FPGA в `GAME MODE` и увидеть на реальном Game Boy тот же результат, который уже получен с внутренним ROM FPGA:

```text
Nintendo logo → black screen
```

## 5. Поэтапный план

### Этап 0. Сохранить рабочий baseline

Сохранить текущую FPGA-конфигурацию и ROM, которые дают `Nintendo logo → black screen`. Не менять содержимое test ROM до завершения первого запуска из Flash.

**Критерий успеха:** baseline можно повторно прошить в FPGA и стабильно воспроизвести на Game Boy.

---

### Этап 1. Подготовить и проверить подключение MX29LV320E

Подключить к FPGA логические address lines, `D0-D7`, `CE#`, `OE#`, `WE#`, питание и обязательную развязку. Подтвердить режим x8 и безопасное состояние всех служебных входов по datasheet конкретного варианта Flash. До подачи питания выполнить проверку соединений и отсутствия коротких замыканий.

На этом этапе не назначать новые точные FPGA/RP2040 pins «по памяти»: сначала сверить package, существующий `PINOUT.md`/constraints и доступные PIO в Diamond.

**Критерий успеха:** электрические соединения проверены; control lines имеют безопасные состояния; `WE#` не может самопроизвольно активироваться при power-up/configuration.

---

### Этап 2. Реализовать в FPGA только чтение Flash

Сделать минимальный консервативный read controller:

```text
set address
→ assert CE#
→ assert OE#
→ wait не меньше требуемого datasheet времени
→ sample D0-D7
→ deassert OE#/CE#
```

Сначала использовать заведомо большие интервалы ожидания. Не добавлять erase/program, пока чтение не проверено.

**Критерий успеха:** FPGA стабильно возвращает одинаковые данные с выбранных адресов Flash; чтение не вызывает конфликтов на data bus.

---

### Этап 3. Провести диагностику FPGA ↔ Flash

Реализовать минимальный тестовый доступ к read controller через уже доступный отладочный путь. Если удобно и подтверждено datasheet, использовать режим чтения идентификаторов Flash; затем вернуться в normal read mode. Проверить несколько адресов, включая границы выбранных диапазонов.

**Критерий успеха:** подтверждены address bus, направление `Flash → FPGA` на `D0-D7`, а также управление `CE#` и `OE#`; чтение повторяемо.

---

### Этап 4. Добавить Flash programmer FSM в FPGA

По command table datasheet реализовать минимальные операции:

- `READ`
- `ERASE` — сначала выбранная простая стратегия для прототипа
- `PROGRAM`
- `STATUS` / busy polling
- timeout и явный error result
- возврат в read mode после завершения или ошибки

Отделить низкоуровневые циклы Flash от интерфейса SPI. Все command sequences и timings брать из datasheet точного варианта MX29LV320E.

**Критерий успеха:** симуляция или стендовый тест показывает правильную последовательность address/data/control cycles; `WE#` активируется только в `PROGRAMMER MODE`.

---

### Этап 5. Зафиксировать безопасные режимы GAME / PROGRAMMER

Добавить явный выбор владельца Flash bus.

В `GAME MODE`:

- address/control формирует Game Boy interface;
- разрешено только чтение Flash;
- `WE#` всегда неактивен;
- programmer не может управлять Flash.

В `PROGRAMMER MODE`:

- Game Boy side отключена от управления Flash;
- Flash controller принимает команды от programmer path;
- запись разрешена только после явного выбора режима.

Для первого прототипа допустим jumper, отдельный вход, отдельная FPGA-сборка или другое простое ручное переключение. Конкретный вариант выбрать с учётом безопасности питания и доступного pinout.

**Критерий успеха:** невозможно получить одновременное управление Flash со стороны Game Boy logic и programmer; переключение режима однозначно наблюдаемо.

---

### Этап 6. Поднять SPI RP2040 ↔ FPGA

Соединить логические сигналы `SCK`, `MOSI`, `MISO`, `CS#` и общий `GND`. Выбрать конкретный SPI mode, начальную низкую частоту и простой версионируемый протокол.

Минимальный набор команд верхнего уровня:

- получить version/capabilities;
- прочитать диапазон Flash;
- запустить erase;
- записать диапазон;
- получить status/error.

Сначала проверить только обмен с регистром версии или фиксированной сигнатурой, без обращения к Flash.

**Критерий успеха:** RP2040 многократно получает от FPGA правильную фиксированную сигнатуру без ошибок транзакций.

---

### Этап 7. Прочитать Flash через полный тракт

Добавить простую USB-команду на RP2040 для чтения диапазона:

```text
PC → USB → RP2040 → SPI → FPGA → Flash
Flash → FPGA → SPI → RP2040 → USB → PC
```

Снять dump нескольких диапазонов и проверить повторяемость. Пока ничего не стирать.

**Критерий успеха:** повторные чтения одного диапазона совпадают байт-в-байт; PC получает корректную длину и статус операции.

---

### Этап 8. Первый erase

Перейти в `PROGRAMMER MODE`, выполнить erase по datasheet и дождаться завершения через status polling с timeout. После завершения прочитать несколько участков, включая начало, середину и конец затронутого диапазона.

**Критерий успеха:** проверенные байты находятся в erased state, операция завершается явным success status и не оставляет Flash в command/status mode.

---

### Этап 9. Записать небольшой test pattern

Не начинать с ROM. Сначала записать короткий диагностический pattern с разными битовыми комбинациями, затем 256-байтовую последовательность. Прочитать её обратно через полный путь и сравнить.

При несовпадении отчёт должен содержать минимум:

```text
address
expected byte
actual byte
```

**Критерий успеха:** оба pattern проходят полный byte-for-byte verify; повторный цикл erase/program/verify также проходит.

---

### Этап 10. Записать известный test ROM

Использовать ровно тот ROM, который уже работает из внутренней памяти FPGA. Записать его с начала Flash. Не добавлять MBC и не менять программу ROM в том же эксперименте.

**Критерий успеха:** programmer сообщает правильный объём записанных данных, завершение без timeout/error и переходит к verify.

---

### Этап 11. Выполнить обязательный полный verify

Прочитать назад весь записанный диапазон и сравнить байт-в-байт с исходным `.gb`. Проверять нужно данные, пришедшие через реальный путь `Flash → FPGA → RP2040 → PC`, а не внутренний буфер отправителя.

Ожидаемый итог:

```text
written:  N bytes
verified: N bytes
result:   VERIFY OK
```

При первой ошибке вывести адрес, ожидаемое и фактическое значения; запуск на Game Boy не выполнять.

**Критерий успеха:** весь ROM совпадает без единой ошибки.

---

### Этап 12. Запустить Game Boy из внешней Flash

Отключить programmer, безопасно перейти в `GAME MODE`, выполнить power cycle и дать FPGA выдавать ROM bytes уже из MX29LV320E.

**Критерий успеха:** на реальном Game Boy воспроизводится baseline:

```text
Nintendo logo → black screen
```

Это закрывает milestone «Game Boy загружает ROM из внешней Flash».

---

### Этап 13. Усилить доказательство выполнения кода

Только после успешного запуска известного ROM подготовить простой diagnostic ROM с однозначным визуальным результатом: заливкой, полосами, шахматным узором или изменением палитры. Сначала проверить его из внутренней памяти FPGA, затем записать во Flash с verify и повторить тест.

**Критерий успеха:** одинаковый диагностический результат получается как с internal ROM, так и с external Flash.

---

## 6. Что пока не делать

До закрытия milestone внешней Flash не расширять область отладки:

- не реализовывать MBC и bank switching;
- не подключать FRAM и saves;
- не делать USB-transfer сохранений;
- не разрабатывать автоматический арбитраж одновременного доступа Game Boy/RP2040;
- не оптимизировать скорость SPI и Flash controller раньше стабильной работы на низкой скорости;
- не проектировать final PCB и корпусную компоновку;
- не записывать полный 4 MB ROM, если 32 KB test ROM ещё не проходит verify;
- не менять одновременно ROM, bus interface и Flash controller в одном тесте;
- не фиксировать неподтверждённые точные назначения FPGA/RP2040 pins.

---

## 7. Рекомендуемый порядок диагностики при сбое

```text
Питание и safe states
        ↓
статические control lines
        ↓
чтение Flash локально из FPGA
        ↓
SPI RP2040 ↔ FPGA без Flash
        ↓
чтение Flash через полный тракт
        ↓
erase
        ↓
короткий pattern + verify
        ↓
полный test ROM + verify
        ↓
GAME MODE на реальном Game Boy
```

На каждом шаге сохранять фактический результат и не переходить дальше при нестабильности.

## 8. Ближайший конкретный шаг

Подготовить проверенную таблицу **логических** соединений `MachXO2 ↔ MX29LV320E` и минимальный read-only Flash controller.

Перед монтажом:

1. Сверить datasheet точного варианта MX29LV320E и режим x8.
2. Проверить питание, decoupling и безопасные состояния `CE#/OE#/WE#` и служебных входов.
3. Сопоставить только логические сигналы `MEM_A`, `D0-D7`, `CE#`, `OE#`, `WE#` с уже проверенным FPGA pinout.
4. Зафиксировать подтверждённые физические назначения отдельно в `PINOUT.md` и constraints.
5. Реализовать первый тест: стабильное повторяемое чтение нескольких адресов без erase/program и без RP2040.

Ближайшая граница готовности: **FPGA надёжно читает MX29LV320E; Flash ещё ни разу не стиралась и не программировалась.**
